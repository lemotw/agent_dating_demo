# 產品需求與方向

本文件整理原型形成過程中的需求與建議，不代表以下功能均已實作。

## 一、概念演進

### 最初：Agent 主題聊天室

- 首頁提供聊天室大廳。
- 一位使用者設定主題並開房，另一位加入；每房兩位人類、兩個 Agent。
- 兩個 Agent 針對主題聊天，人類旁觀。
- 最初技術構想為一對一 WebRTC、STUN。

實作材料：`agent-lounge.html`。目前僅單頁模擬開房、加入、聊天、暫停與重播。

### 中間方向：人可監督與介入的 Agent 社交

使用者希望看著自己的 Agent 進入房間，並能引導或修正其談話。

當時提出的功能方向：

- 公開對話與私人指導區分離。
- 引導下一回合，明示指令何時生效。
- 暫停並作廢未送出的舊草稿。
- 對已公開訊息發出可追溯的更正，不僅修改本機畫面。
- 自動發言、逐句審核、人類接管等模式。
- 區分事實更正、立場、語氣及話題指導；人類指令不一定是客觀真相。
- 短期指令不自動寫成永久記憶；長期偏好應經使用者確認。

這些為設計方向，並未全部實作進前版 HTML。

### 目前：Agent Dating App

核心定位：Agent 幫助使用者被理解、交換授權背景、找到值得親自確認的問題；是否繼續由真人決定，而不是讓 Agent 替人選擇伴侶。

## 二、使用者提出的核心流程

1. 註冊後，Agent 深入了解使用者自身故事與想遇到的人。
2. 取得背景後，提供含照片與基本資料的左滑／右滑探索。
3. 雙向配對後，双方 Agent 交流各自使用者的背景與期待。
4. 生成報告，使用者閱讀後決定是否繼續聊天。

## 三、原型如何呈現

| 階段 | 已實作的示範 | 尚未實作 |
| --- | --- | --- |
| 註冊 | 暱稱、18+ 與原型聲明 | 真實帳號、年齡驗證 |
| 深度訪談 | 六個固定方向、跳過、示範回答 | 動態追問、語意摘要、長期記憶 |
| 背景授權 | 可編輯摘要、逐項勾選，預設不分享 | 後端權限與可驗證存取控制 |
| 探索 | 三個虛構成人角色、按鈕及觸控滑卡 | 真實照片、偏好篩選、推薦服務 |
| 雙向配對 | 預設互相喜歡狀態、再次確認授權 | 真實雙人配對與狀態同步 |
| Agent 交流 | 六則模板訊息、暫停／繼續／結束 | 模型與回合協調服務 |
| 報告 | 授權欄位對照、來源、未知資訊、破冰問題 | 真實語意分析與可靠性驗證 |
| 真人聊天 | 邀請、模擬對方同意、本機訊息 | 對方在線、訊息傳輸、封鎖與檢舉 |

## 四、背景與同意邊界

- 私人訪談原文與可分享摘要必須為不同資料層。
- 預設不分享，不能將完成訪談視為對外揭露的同意。
- 交流前固定本次授權摘要與版本，並保留同意紀錄。
- 個人故事不預填到可分享摘要，避免無意外洩。
- 未授權欄位不可送入對方 Agent 的上下文；不能只靠 prompt 要求保密。
- 不推測性向、健康狀態等敏感特徵；必要偏好由使用者自願明確提供。
- 撤回只能阻止後續使用，不能宣稱可收回對方已看見或留存的資訊。
- 不以揭露更多隱私作為提高配對機會的條件；問題可跳過。
- 模型供應商的資料處理、保存期限與刪除政策需在真實產品上明確說明。

## 五、報告應該回答什麼

1. 雙方各自表達了什麼期待？
2. 有哪些值得真人探索的共同話題？
3. 哪些差異需要本人確認，而不是 Agent 自行判斷？
4. 哪些資訊未提供或未驗證？
5. 可以從哪個低壓、具體的問題開始聊？

避免假精確的相容度百分比、心理診斷、替人承諾或宣稱能預測戀愛結果。現在的原型僅將欄位對照組成討論提綱，沒有真正判斷適配程度。

## 六、建議開發順序

### Phase 1：驗證互動

- 測試訪談負擔是否太高，考慮先短訪談、後漸進深入。
- 驗證使用者是否理解「只對自己的 Agent 說」與「可向對方分享」的差別。
- 驗證報告是否有助真人開聊，而非製造額外焦慮。
- 觀察訪談完成率、授權理解程度、配對後閱讀與聊天意願，不只看停留時間。

### Phase 2：串接真實服務

建議模組：帳號與成人資格、個人檔案、私人訪談、授權摘要、喜歡與雙向配對、Agent runtime、回合協調、報告、真人聊天、檢舉與封鎖。

最小流程狀態：

```text
onboarding → interview → profile_ready → discovering
→ matched → consent_pending → agent_exchange
→ report_ready → human_consent_pending → human_chat
```

還需有 declined、cancelled、failed 等終止與失敗狀態。雙方授權必須獨立確認，配對、交流與真人聊天不得共用一個含糊的同意旗標。

每次 Agent 發送前重新檢查：配對有效性、雙方授權版本、暫停狀態與回合 ID。用去重、有限輪數、時間與 token 預算，避免重複發送或無限對話。

### Phase 3：可靠性與安全

- Agent 不得把對方提供的內容當成系統指令，需防 prompt injection 與索取隱私。
- 真實上線前具備封鎖、檢舉、解除配對、反騷擾與照片授權機制。
- 提供更正、刪除、撤回授權及資料保存期限。
- 評估報告是否錯引、洩漏未授權資訊、做出缺乏證據的相容性判斷。
- 對真人訊息、模型訊息、系統狀態與示範資料提供清楚標示。

## 七、技術選型

產品的核心不是 WebRTC，而是可信的背景授權與配對後探索。

- Agent 在伺服器執行時，可先採 WebSocket 或 SSE + HTTP，讓狀態、授權、回合與斷線恢復集中管理。
- 若之後需要兩端自帶本機 Agent，才評估 WebRTC DataChannel。
- STUN 不提供 signaling，也不是訊息中繼；STUN-only 無法保證穿越所有 NAT／防火牆。
- 正式 WebRTC 仍需 signaling、失敗處理，必要時 TURN fallback。
- 模型 API key 不可放在公開 HTML 中。
